Architecture Gesta et parcours de visualisation des offres

Une vue d'ensemble de l'application et du trajet complet d'une offre, du composant React jusqu'à SQLite puis de nouveau vers l'interface.

Architecture générale

Le projet est un monorepo npm composé de deux workspaces TypeScript. Le frontend React/Vite communique avec une API Express ; l'API porte les règles métier et utilise une base SQLite locale.

Frontend

React + Vite

Pages, composants, hooks, services HTTP, modèles et type guards.

API

Express

Routes, authentification, autorisation, validation et réponses JSON.

Métier

Services + repositories

Visibilité selon le profil, requêtes SQL et mapping des données.

Données

SQLite

Offres, entreprises, années académiques, périodes et utilisateurs.

Le backend suit le flux controller → service → repository → SQLite. Les mappers séparent les lignes SQL, les objets métier et les DTO publics. Le frontend suit le flux page → hook → service → API et délègue le rendu aux composants réutilisables.

1. Départ dans le composant React

App.tsx appelle useAuth une seule fois. Une fois l'utilisateur connecté, il rend la route /offres et transmet le token ainsi que le callback de déconnexion à OffersPage. La permission côté interface masque la route pour les profils non concernés, mais elle ne remplace jamais le contrôle backend. 

const { offers, isLoading, error } = useOffers(token, onUnauthorized);

if (error) return <ErrorState message={error} />;
if (isLoading) return <LoadingState />;
if (offers.length === 0) return <EmptyState message="Aucune offre à afficher." />;
return <OfferTable offers={offers} />;

2. Hook et service HTTP

useOffers.ts lance l'appel dans un useEffect. Un AbortController évite de mettre à jour un composant après son démontage. offers.service.ts envoie le jeton brut dans Authorization, sans préfixe Bearer. 

fetch("/api/offers", {
  headers: { Authorization: token },
  signal,
});

3. Proxy puis pipeline Express

En développement, Vite transmet /api/offers au backend sur le port 3000 en retirant le préfixe /api. Dans app.ts, la route est protégée par authenticate. Puis authorize(canListOffers) vérifie le droit d'accès. 

app.use("/offers", authenticate, createOffersRouter(offersService));

router.get("/", authorize(canListOffers), (req, res) => {
  res.json(offersService.listOffers(getCurrentUser(req)).map(toOfferDto));
});

4. Service métier et base de données

Le service choisit le filtre selon le profil. L'administrateur voit tout, l'étudiant voit les offres publiées et un contact déposant voit ses propres offres. Le repository exécute ensuite une requête paramétrée avec des jointures vers l'entreprise, l'année académique et la période.

ProfilFiltre métierRéponse
Administrateur{}Toutes les offres.
Étudiantstatus = PUBLISHEDOffres publiées.
Contact déposantdepositor_contact_id = user.idOffres déposées par ce contact.
Contact sans rôle déposantRefus métier403 FORBIDDEN
 
SELECT o.id, o.title, o.description, o.status,
       c.short_name AS company_short_name,
       ay.label AS academic_year_label, p.code AS period_code
FROM offers o
JOIN companies c ON c.id = o.company_id
JOIN academic_years ay ON ay.id = o.academic_year_id
JOIN periods p ON p.id = o.period_id
WHERE (@status IS NULL OR o.status = @status)
  AND (@depositorContactId IS NULL OR o.depositor_contact_id = @depositorContactId)
ORDER BY ay.start_date DESC, o.created_at DESC;

5. Retour, mapping et affichage

Les lignes SQL sont converties par toOffer, puis réduites au contrat public par toOfferDto. Le frontend vérifie le statut HTTP et la structure avec readJson et isOfferList. Enfin OfferTable traduit les codes de période et de statut avec utils/labels.ts.

Ajout d'un filtre par période

Le modèle expose déjà period et le repository joint déjà la table periods. Le filtre doit donc traverser toute la chaîne, de l'interface jusqu'au paramètre SQL, sans déplacer la règle d'accès du backend vers le frontend.
