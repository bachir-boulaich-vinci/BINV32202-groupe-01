Matrice de Traçabilité - Conformité Web 2

Attente ou convention de Web 2 (source) Guide examiné (fichier et passage) Correspondance Écart ou ajout proposé
1. Organisation du projet & Structure
[seance-01.pdf, page 21], [seance-09.pdf, page 3-19], [seance-10.pdf, page 2-15]		 docs/architecture.md (Architecture générale)
frontend/tsconfig.app.json (Configuration globale)		 Partielle. L'architecture backend est documentée, mais les règles de répertoires frontend (assets vs public, models) ne figurent pas dans les guides. Ajout proposé : Rédiger un document docs/architecture-frontend.md détaillant l'arborescence imposée et l'usage strict de public/ vs src/assets/.
2. Conventions Backend & API REST
[seance-02.pdf, page 3-18], [seance-03.pdf], [seance-04.pdf]		 backend/API.md (Contrat API)
.github/pull_request_template.md (Vérifications PR)		 Forte. Le document API couvre les requêtes. Le template PR force la validation des erreurs 400, 401, 403, 404. Écart : Le PR template ignore les codes de succès (201, 204) et le 409 Conflict. Ajout : Ajouter ces codes dans la checklist de la Pull Request.
3. Documentation d'API
[seance-02.pdf, page 11-18]		 backend/API.md (Contrat API) Complète. L'utilisation de Markdown est explicitement validée comme l'une des 3 approches. Ajout proposé : Configurer une règle de linter JSDoc pour garantir que le code source soit également commenté, renforçant le fichier Markdown.
4. Sécurité, JWT et Mots de passe
[seance-03.pdf, page 8-15], [seance-04.pdf, page 2-14]		 docs/workflow-visualisation-offre.html (Autorisations)
backend/.oxlintrc.json (Linter)		 Partielle. Le flux d'autorisation est décrit. Cependant, aucune règle stricte ne bloque l'usage de bcrypt.hashSync() (synchrone). Ajout proposé : Ajouter une règle Oxlint interdisant l'import ou l'usage des méthodes synchrones de bcrypt. Créer un script vérifiant que JWT_SECRET dans .env fait plus de 32 caractères.
5. Programmation Fonctionnelle & TypeScript
[seance-01.pdf, page 7-19]		 backend/tsconfig.json et frontend/tsconfig.app.json (strict: true)
backend/.oxlintrc.json		 Forte. Le refus de any et les vérifications strictes assurent une base solide. Écart : L'immuabilité (privilégier const) n'est pas garantie par défaut. Ajout : S'assurer que la règle prefer-const est configurée en erreur critique dans Oxlint.
6. HTML & DOM (Sécurité XSS)
[seance-05.pdf, page 6-15], [seance-06.pdf]		 frontend/.oxlintrc.json (Linter frontend) Faible. Les guides ne garantissent pas explicitement l'interdiction de innerHTML. Ajout proposé : Imposer la règle linter react/no-danger (pour dangerouslySetInnerHTML) et bloquer l'usage de innerHTML natif.
7. Conventions React & JSX
[seance-07.pdf], [seance-08.pdf], [seance-10.pdf]		 frontend/.oxlintrc.json (Règles React) Forte. L'orchestrateur garantit la conformité basique du code React via les règles standards. Écart : Pas de vérification stricte sur la prop key unique issue de la BDD (et non de l'index). Ajout : Renforcer Oxlint avec l'activation de react/jsx-key en mode strict.
8. Style et Material UI (MUI)
[seance-09.pdf, page 5-19]		 Aucun guide identifié sur la gestion du style. Absent. Les conventions CSS Modules, ThemeProvider ou l'usage exclusif de la prop sx ne sont ni documentés ni automatisés. Ajout proposé : Rédiger docs/frontend-style.md. Ajouter des règles Oxlint interdisant l'attribut style={{...}} classique au profit exclusif de sx ou des classes CSS Modules.
9. Gestion de l'état avec useState & Hooks
[seance-11.pdf à 14.pdf]		 frontend/.oxlintrc.json (react/rules-of-hooks et exhaustive-deps) Forte. L'usage de base des hooks et l'ordre d'appel sont strictement encadrés par le Linter. Écart : Les mutations directes d'état (push, splice) ne sont pas bloquées computationnellement. Ajout : Configurer des règles d'immuabilité (ex: plugin fonctionnel) pour interdire toute mutation directe de tableau/objet dans React.
